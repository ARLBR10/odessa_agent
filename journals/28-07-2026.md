## Kernel manifest synchronization repair

- A `repo sync` tried to rebase the local Odessa kernel branch (fork commit
  `5be9b397`) onto LineageOS's historical SM6150 kernel commit `112b525`,
  because `manifests/odessa.xml` still named the public repository. The shallow
  clone made the histories appear unrelated, producing a 9,272-commit replay
  and an F2FS conflict. The rebase was aborted; no kernel source was changed.
- Verified the intended kernel tip `wip/bpf-backport-4.14.357`
  (`295fa6418564d0b5a43742aae8b35dcb60754f67`) is a fast-forward of the fork's
  prior `lineage-23.2` tip and pushed it to
  `ARLBR10/android_kernel_motorola_sm6150:lineage-23.2` without force.
- Updated `manifests/odessa.xml` to pin that exact fork commit. This makes the
  BPF-backport kernel reproducible and prevents Repo from attempting to replace
  it with the historical public baseline.

## BPF backport bootloop investigation

- User correction: exact commit `df9da243d122` was independently built and ran
  on the phone; it is the proven-good hardware boundary. The bootloop was added
  by `37e035f8c918`, `eb0458ea6a0f`, or the later networking changes, which have
  not yet been isolated from one another on hardware.
- Found one definite incomplete import in `eb0458ea6a0f`: the conversion of
  `struct irq_work::flags` to `atomic_t` omitted the matching
  `kernel/printk/printk.c` initializer change from reference commit
  `25343fb51d17`. Changed `wake_up_klogd_work.flags` from `IRQ_WORK_LAZY` to
  `ATOMIC_INIT(IRQ_WORK_LAZY)`. This is correctness-required but is not yet
  proven to be the hardware bootloop root cause.
- Audited Android 16's boot-loaded BPF objects. `CONFIG_NET_ACT_BPF` is not
  required for `BPF_PROG_LOAD`; do not enable it as a speculative fix. The
  current tree contains the early-loader's BTF, ringbuf, DEVMAP_HASH, map, and
  program types, but actual verifier/JIT behavior still needs hardware evidence.
- `m -j8 bootimage` rebuilt `kernel/printk/printk.o` and completed successfully
  in 8m41s. Result: `out/target/product/odessa/boot.img`, 67,108,864 bytes,
  SHA-256 `3081a284ec749ae8cce667746f49bff002adb4213a743ee50d18246744d719e4`.
  Build log: `/tmp/opencode/odessa-bootimage-20260728.log` (local, untracked).
- Static audit found no single proven loader crash, but the runtime-sensitive
  ARM64 BPF JIT and virtual-address-layout rework begins at `37e035f8c918`.
  Prepared an unbuilt candidate that leaves later BPF/network APIs in place but
  restores `arch/arm64/net/bpf_jit_comp.c`, `arch/arm64/include/asm/memory.h`,
  and `arch/arm64/configs/vendor/odessa_defconfig` exactly to the known-good
  `df9da243d122` versions. Also fixed two real `net/core/dev.c` bugs: a
  `kvzalloc()` allocation was freed with `kfree()` on error, and normal
  `free_netdev()` leaked `dev->_rx`. No build was run for this candidate.
- Hardware result: that candidate still bootlooped. Therefore the restored JIT,
  ARM64 virtual-address layout, and defconfig changes are not the sole cause.
  Removed those three reversions so they do not remain stacked on later tests;
  retained the two independently valid `net/core/dev.c` memory fixes.
- User clarified the hardware oracle: every kernel is tested through a newly
  built and flashed recovery. This failure occurs before Recovery UI/ADB, so it
  is an early kernel/recovery boot regression and not Android's controlled
  `netbpfload` reboot. The failed Image was 33,189,912 bytes, effectively the
  same size as previously bootable 4.14 kernels, ruling out simple Image growth.
- Prepared the next unbuilt isolation candidate by disabling the two new
  `kernel/trace/bpf_trace.c` initcalls introduced in `37e035f8`: module raw
  tracepoint notifier registration and per-CPU BPF signal irq-work setup.
- That trace-init candidate still bootlooped, so both initcalls were restored.
- Prepared the next unbuilt recovery candidate in `net/core/dev.c`: retain RX
  queue allocation but call `xdp_rxq_info_unused()` instead of registering XDP
  metadata for every queue during net-device creation. This isolates a runtime
  path absent at the known-good boundary while preserving structure/API changes.
