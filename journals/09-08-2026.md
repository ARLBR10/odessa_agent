## Evidence Carry-Forward Rule (Project Decision)

User decision (2026-08-09): do not insist on re-running the full hardware matrix
on every new `TRY##` build. A function is `PASS` on the current baseline if its
most recent hardware-validated evidence is on an earlier build AND the change
under test in the new build does not plausibly affect that function.

- This rule is now rule 7 in `DEVICE_STATE.md` Update Rules.
- Functions with open `ODESSA-NNN` issues, blocked prerequisites, or a current
  build that changed the relevant code path keep their existing `FAIL`,
  `PARTIAL`, `BLOCKED`, or `UNTESTED` status until the relevant evidence is
  refreshed.
- Charter-MUST functions on the current baseline (boot, OTA, Recovery install,
  SELinux, LineageOS Recovery as install path) are re-validated on every build
  because they are how we know the build itself is shippable. The full
  re-validation does not need to extend to functions the build did not change.

The matrix has been updated accordingly. Specific items left untouched because
they are still open or have a code-path-touching change in TRY28:
`ODESSA-004`, `ODESSA-009`, `ODESSA-010`, `ODESSA-011`, `ODESSA-012`,
`ODESSA-013`, `ODESSA-014`, `ODESSA-015`, `ODESSA-016`, boot endurance, suspend
and screen-sleep behaviour, in-system updater, MTP, USB tethering, FM radio, and
the magnetometer.

## Kernel Panic Display Candidate

- The existing kernel panic path already unblanks the console, flushes its
  emergency log, waits for `CONFIG_PANIC_TIMEOUT=5`, and reboots. Pstore is
  also configured, although hardware testing previously proved it unreliable
  on this device.
- The missing display link was confirmed in the exact TRY28 kernel config:
  `CONFIG_DRM_FBDEV_EMULATION` and `CONFIG_FRAMEBUFFER_CONSOLE` were disabled.
  The Qualcomm MSM DRM tree already contains an fbdev helper, but it was not
  compiled or registered.
- Candidate change: enable both options in `vendor/odessa_defconfig`. This is
  the smallest available Linux 4.14 implementation and should put panic kmsg
  text on the panel during the existing five-second timeout.
- This is not the newer DRM panic renderer introduced in Linux 6.10. A styled
  message or QR-code screen would require backporting that subsystem and adding
  panic-safe scanout support to this downstream Qualcomm SDE driver.
- Hardware status: untested. First verify normal Recovery and Android display
  behavior plus `/dev/fb0`; only then run one deliberate SysRq panic with the
  user's explicit agreement. A visible screen is not yet claimed.

- TRY29 has a virtual `/sys/class/graphics/fbcon`, but no framebuffer device in
  `/sys/class/graphics` or `/dev`. Rooted dmesg shows MSM DRM initializes, then
  fbdev creation fails: `failed to get buffer obj iova: -22`.
- The failure occurs while `msm_fbdev_create()` pins the BO returned by

  an address space; retain stolen allocation plus its existing fallback for
  no-IOMMU hardware. No deliberate panic was triggered because no `fb0` existed.

### TRY31 Runtime And Deliberate Panic Result

- User reports TRY31 installed. ADB proves slot `_b`, boot completion, SELinux
  enforcing, and reused incremental `1786303518`. Candidate-specific evidence
  proves TRY31: `/sys/class/graphics/fb0` and `/dev/graphics/fb0` exist; fb name
  is `msm`, virtual size is 4096x2400, and format is 32 bits per pixel.
- Focused rooted dmesg reports `fb0: msm frame buffer device`; the prior
  `failed to get buffer obj iova: -22` is absent. This hardware-verifies the SDE
  address-space accessor fix and resolves the fbdev-registration subproblem.
- After explaining that the operation intentionally crashes and reboots the
  phone, explicit user authorization was obtained to write `c` to
  `/proc/sysrq-trigger`. The user watched the panel.
- FAIL: the current Android frame froze; no kernel text or separate panic screen
  appeared. The phone rebooted after about five seconds. Post-reboot ADB proves
  slot B, `sys.boot_completed=1`, SELinux enforcing, and boot reason
  `kernel_panic`.
- Diagnosis: fbcon renders to its private fbdev buffer, but SurfaceFlinger has
  replaced the active DRM scanout with another framebuffer. The generic panic
  console flush does not switch downstream SDE back to fbdev, and normal atomic
  modesetting is unsafe in panic context. A real implementation requires a
  panic-safe DRM renderer/scanout callback for SDE, conceptually like modern
  DRM panic support rather than another Kconfig toggle.
- Charter review confirms that a visible kernel panic screen, fbcon, pstore, and
  DRM panic are not device-support requirements. The user decided not to pursue
  the optional feature. The experimental defconfig and MSM fbdev accessor
  changes were removed from shipping source; this section remains historical
  evidence of the TRY29-TRY31 experiment.
