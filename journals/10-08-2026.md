- The new initiating path is `pm_runtime_work` -> `ufshcd_runtime_suspend` ->

  not reclassified as crashes.

  made during this investigation.
- Removing the terminal `BUG()` is not a fix: the caller is synchronously
  waiting for a required AOSS response, so that change would replace the reboot
  with an indefinite hang. Investigation must compare the RPMh mailbox/TCS and
  UFS power-transition implementation against a known-stable kernel and the

- The user confirms the spontaneous reboot occurred while the battery was at
  100%, USB charging was connected, and the screen was off. This matches the
  preserved runtime-suspend trace rather than an active-use workload.

## Mailbox retry candidate

- Comparison against the hardware-supported SM6150 reference branch found
  `drivers/soc/qcom/rpmh.c` identical, but Odessa's generic mailbox core lacks
  Qualcomm commit `831c4302961e` (`drivers: mailbox: fix race resulting in
  multiple message submission`).
- `qcom-rpmh-mailbox.c` returns `-EAGAIN` after logging the exact observed
  `TCS Busy, retrying RPMH message send` line. Odessa's current `msg_submit()`
  drops that return code, leaves the request queued, and provides no event that
  resubmits it. The RPMh client then waits forever for the response and reaches
  its terminal `BUG()` path.
- Qualcomm's fix splits submission into `__msg_submit()`, drops the channel
  spinlock, and retries only `-EAGAIN`. Its upstream commit message explicitly
  identifies the resulting failure as a client waiting forever for a response.
  The LineageOS Xiaomi SM6150 reference carries this implementation.
- Restored that focused retry behavior in the Odessa kernel tree. No UFS power
  feature was disabled and the RPMh timeout/`BUG()` path was not hidden. This is
  a source candidate pending compilation, artifact verification, installation,
  and charging/screen-off endurance testing on hardware.
