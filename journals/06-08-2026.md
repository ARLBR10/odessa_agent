# 2026-08-06

## Spontaneous reboots and black screen

- The user reports that TRY26 sometimes restarts to the Motorola logo after
  unattended time, and sometimes has a black screen with mostly no haptic
  response to attempted interaction. The most recent black-screen attempt did
  produce haptic feedback.
- Read-only Android ADB found `odessa`, build timestamp/incremental
  `1785968028` (TRY26), slot `_a`, and only about four minutes of uptime. Both
  `ro.boot.bootreason` and Android bootstat reported `kernel_panic` /
  `kernel_panic,bug`. This differs from the previously documented slot-B
  runtime; how slot A acquired the same TRY26 build was not established.
- ADB root was refused because root access is disabled in Developer options.
  Direct shell reads of `/sys/fs/pstore`, `dmesg`, `/metadata/bootstat`, and the
  DropBox backing directory were therefore denied. Android's `BootReceiver` had
  already copied `console-ramoops-0` into DropBox as `SYSTEM_LAST_KMSG`, so
  `dumpsys dropbox --print` still preserved the crash evidence.
- Five `SYSTEM_LAST_KMSG` entries were present. The first ended in an ordinary
  `reboot`; the following four, dated Aug 5-6, independently contain the same
  kernel panic at approximate uptime 93.3 s, 1,708.4 s, 93.1 s, and 1,817.9 s.
- In every panic, `msm_bus_device 16e0000.ad-hoc-bus` first logs `TCS Busy,
  retrying RPMH message send`, then four `RPMH response timeout` messages at
  10-second intervals for address `0x50000`, followed by `RPMH waiting for
  interrupt from AOSS`. `drivers/soc/qcom/rpmh.c:209` executes `BUG()` and the
  kernel reports `Kernel panic - not syncing: Fatal exception`, waits five
  seconds, and restarts.
- The initiating task is always `ufs_clk_gating_0` / `ufshcd_gate_work`. The
  complete relevant call path is `ufshcd_gate_work` -> `ufshcd_setup_clocks` ->
  `ufs_qcom_set_bus_vote` -> `msm_bus_scale_client_update_request` ->
  `update_request_adhoc` -> `update_client_paths` -> `msm_bus_commit_data` ->
  `rpmh_write_batch`. This establishes an AOSS/RPMh power-vote failure during a
  UFS storage clock transition, not an Android framework, app, GPU, or
  SurfaceFlinger crash.
- Source inspection confirms the fatal `BUG()` and timeout loop are old vendor
  RPMh code and are unchanged between the kernel's `lineage-23.2` baseline and
  current HEAD. Removing `BUG()` would only hide the terminal symptom while the
  required AOSS response remains lost; the repair must address the power/RPMh,
  mailbox/TCS, or UFS transition failure.
- The long-uptime crash logs show normal suspend/wake activity shortly before
  the TCS becomes busy. During the final 40-50 seconds, only RPMh timeout
  messages remain. Because display and haptic power transitions also depend on
  the always-on power subsystem, this is a plausible explanation for the black
  and mostly unresponsive interval before reboot, but the logs do not prove all
  reported black-screen episodes are this same failure.
- A live `dumpsys display`, `dumpsys power`, and SurfaceFlinger snapshot found
  the phone normally asleep after a screen timeout: display policy and panel
  state were off, SurfaceFlinger remained alive, and Adreno was initialized.
  No display/GPU fatal error was found. This snapshot does not reproduce a
  failed wake and therefore cannot close the separate black-screen diagnosis.
- Preserved last-kmsg also shows `/debug_ramdisk/magisk --service`; root was
  installed separately even though adbd root is currently disabled. Repeat the
  eventual fix validation on an unrooted build so Magisk/modules can be excluded.
- Opened `ODESSA-009` (`P1`) for the repeatable RPMh/UFS kernel panic and
  `ODESSA-010` (`P1`) for the black/unresponsive screen. Raw logcat, DropBox,
  display, power, input, SurfaceFlinger, and battery captures remain only under
  `/tmp/opencode`; they contain device identifiers and personal/app data and
  must not be committed or shared unredacted.

## Sensor, fingerprint, display, and addon verification (slot A, TRY26)

Read-only ADB on the physical device confirmed the bring-up items the user
asked about. All evidence below is from `adb shell` against the connected
`odessa`, with the system reporting build
`23.2-20260805-UNOFFICIAL-odessa` (timestamp `1785968028`), slot
`ro.boot.slot_suffix=_a`, `sys.boot_completed=1`.

- **Fingerprint (HIDL).** `dumpsys fingerprint` returns
  `FingerprintProvider/defaultHIDL` with `prints:[{id:0,count:2,...}]` (one
  enrolled print touched twice during enrollment), `HAL deaths since last
  reboot: 0`, no permanent or timed lockout. `service list` includes
  `fingerprint: [android.hardware.fingerprint.IFingerprintService]`,
  `biometric:`, `auth:`, and the LineageOS `lineagetrust:` service. The user
  reports it has worked since the BT/Wi-Fi fix; resolves `ODESSA-003`.
- **Sensors.** `dumpsys sensorservice` reports `Total 39 h/w sensors, 39
  running, 0 disabled clients`. All four charter-MUST sensors are present and
  exercised:
  - Accelerometer — `icm4x6xx Accelerometer` (TDK-Invensense, ver 306), 3
    active clients (`FaceDownDetector`, GMS `personalsafety.ars`,
    location collection). Raw + uncalibrated + wake variants.
  - Gyroscope — `icm4x6xx Gyroscope` (same chip), used by
    `WindowOrientationListener` via the `Display Rotate` composite.
  - Light — `stk_stk3a5x Ambient Light Sensor` (sensortek, ver 113), 2 active
    clients = `AutomaticBrightnessController` + `BrightnessTracker`.
  - Proximity — `stk_stk3a5x Proximity Sensor` (sensortek, ver 113), 1 active
    client = SystemUI `ThresholdSensorImpl` (the call-screen-off hook).
  - Plus `pedometer` (step counter + step detector), `sns_tilt`,
    `sns_smd` (significant motion), `qti.sensor.cmc`, Motorola
    `com.motorola.sensor.*` (Flat Up/Down, Stowed, Camera Gesture, ChopChop,
    Moto Glance, Lift to Silence/View, Flip to Mute, Off Body, Log).
- **Magnetometer gap.** `pm list features` declares
  `feature:android.hardware.sensor.compass` but the sensor list contains no
  `android.sensor.magnetic_field` handle, and 9-axis fusion reports
  `9-axis fusion disabled (0 clients)`. Charter treats magnetometer as
  "other sensors" (SHOULD) and the user has not yet hardware-tested; opened
  `ODESSA-011` (P3) so the gap is not forgotten.
- **Display.** `wm size` = 1080×2400, `wm density` = 420, vsync 60.000004 Hz,
  `supportedHdrTypes=[2, 3, 4]` (HDR10, HLG, HDR10+) with max luminance 450
  nits. Resolution and density match stock G9 Plus. Front camera cutout
  recorded in the panel waterfall insets. HDR playback path not yet exercised
  by an app.
- **MindTheGapps (addon, not bundled).** `pm list packages` shows
  `com.google.android.gms` `versionName=26.29.32 (260400-956293556)` (installed
  2026-08-05 19:44:41), `com.android.vending` `52.5.22-34`,
  `com.google.android.gsf` `16-13343139`, plus the MindTheGapps overlays
  (`com.mtg.gmssettingsoverlay`, `com.mtg.gmssetupwizardoverlay`,
  `com.mtg.gmsoverlay`, etc.). Features `GOOGLE_BUILD` and
  `GOOGLE_EXPERIENCE` are declared. Play Integrity is not exercised in this
  build; no claim permitted.
- **Magisk (addon, not bundled).** `ps -A` shows `magiskd` (PID 1285, root
  user) running. `/product/bin/su` is a symlink to `./magisk`. From an
  unprivileged `adb shell`, `su -c id` returns
  `uid=0(root) gid=0(root) groups=0(root) context=u:r:magisk:s0`.
  `magisk -V` = 30700 and `Denylist is enforced`. `/debug_ramdisk` and
  `/product/bin/magisk{,policy}` are Magisk bind mounts in `/proc/mounts`. The
  kernel cmdline reports `androidboot.verifiedbootstate=orange`, the expected
  state for the bring-up vbmeta `--flags 3` documented in MEMORY.md. ADB
  root is still disabled in Developer options, so the root capability is
  available to apps that request it but not to the adb shell directly.
- **Slot A, not B.** `getprop ro.boot.slot_suffix = _a`. The 2026-08-05
  journal also recorded A; the user-side historical B-slot runtime is not
  reproducible from this boot. The matrix and `ODESSA-009` evidence must be
  re-stamped for slot A.
- **Firmware ID drift.** `ro.build.fingerprint` =
  `motorola/odessa_retail/odessa:11/RPAS31.Q2-59-17-4-5-5/af8e3:user/release-keys`.
  MEMORY.md validates `RPAS31.Q2-59-17-4-3-9` as the safe restore. The phone
  now runs **4-5-5**, which has not been validated the same way and may be
  the actual cause of the AOSS/RPMh stall. Opened `ODESSA-012` (P2) — the
  charter's `Firmware` section requires us to assert on known-working
  firmware, so the choice is to (a) restore 4-3-9 and re-validate, (b) re-run
  the bring-up suite against 4-5-5 and add it to the wiki, or (c) pin a new
  restore package.
