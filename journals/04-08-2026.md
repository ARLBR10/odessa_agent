# 2026-08-04

## Wi-Fi and Bluetooth failure diagnosis

- The installed baseline remains TRY23. The phone was initially in Recovery;
  with user permission it was rebooted once into Android for read-only ADB
  diagnostics. No partition was flashed, erased, formatted, or otherwise
  written by the agent.
- Kernel history does not contain a direct OpenELA/BPF-era change to
  `drivers/staging/qcacld-3.0`, `drivers/staging/qca-wifi-host-cmn`, CNSS,
  `drivers/bluetooth`, or `net/bluetooth`. The large indirect networking import
  is kernel commit `8c13ed9d15ab`, but runtime evidence does not identify it as
  the radio initialization failure.
- Wi-Fi runtime evidence: signed `wlan.ko` loads successfully, but no `wlan0`
  interface is created. `/vendor/firmware_mnt` is neither present nor mounted.
- Bluetooth runtime evidence: the HIDL service registers, opens `/dev/ttyHS0`,
  powers the controller, communicates over UART, and changes baud rate. It then
  fails to open `/bt_firmware/image/apbtfw11.tlv` and its NVM data, reports
  `NVM file not found`, and the framework Bluetooth process repeatedly aborts.
- `/vendor/etc/fstab.qcom` already has slot-selected mounts for `modem` at
  `/vendor/firmware_mnt`, `bluetooth` at `/vendor/bt_firmware`, `dsp` at
  `/vendor/dsp`, and `fsg` at `/vendor/fsg`. The block-device symlinks exist,
  but all four mountpoint directories are absent from the exact vendor output.
- Current `hardware/qcom-caf/common` and `hardware/motorola` define Soong
  `mkdir` modules for these mountpoints. The migrated SM6150 product did not put
  those modules in `PRODUCT_PACKAGES`, so the definitions existed in the build
  graph but did not install the directories into the vendor image.
- Added `vendor_bt_firmware_mountpoint`, `vendor_dsp_mountpoint`,
  `vendor_firmware_mnt_mountpoint`, and `vendor_fsg_mountpoint` to
  `device/motorola/sm6150-common/common.mk`. This matches current LineageOS
  Qualcomm/Motorola device-tree practice and covers every missing fstab target.
- `git diff --check` passes. Per project workflow, no Android build was run by
  the agent; the user will run the supplied build command. The fix remains
  unbuilt and requires exact-artifact and hardware verification.

## TRY24 hardware result and Wi-Fi follow-up

- The user sideloaded TRY24, but stock partition-table restoration selected old
  slot A. Android reported old timestamp `1785802301`, proving TRY24 had not
  booted. With explicit approval, `fastboot set_active b` selected slot B; it
  booted timestamp `1785886110`, matching the current OTA metadata. No image was
  flashed by the agent.
- Current OTA SHA-256 is
  `f3b351655782559d63985747beff47a7ac56c23771daa04733003db7a1b02532`.
  The named TRY24 ZIP is another mutable hardlink and is not preserved evidence.
- TRY24 mounts `modem_b` at `/vendor/firmware_mnt`, `dsp_b` at `/vendor/dsp`,
  `bluetooth_b` at `/vendor/bt_firmware`, and `fsg_b` at `/vendor/fsg`. The
  Odessa board-data bind mount is active.
- The user enabled and tested Bluetooth successfully. The user also reports
  audio now works; exact speaker/microphone/headset/scrcpy coverage remains
  incomplete. This hardware-verifies the Bluetooth mountpoint fix and strongly
  connects the audio improvement to the restored DSP mount.
- Wi-Fi still fails. `wlan.ko` loads and ICNSS processes one `REGISTER_DRIVER`
  event, but ICNSS debug stats show zero `SERVER_ARRIVE`, zero firmware-ready/QMI
  requests, state only `SSR REGISTERED | PDR REGISTERED`, and no `wlan0`.
- Every `/vendor/rfs` path is absent. Commit `31eea31c` removed the legacy
  generated integration under the assumption that modern Qualcomm common Soong
  modules replaced it, but this product never inherited
  `hardware/qcom-caf/common/common.mk`. Therefore none of those RFS symlink
  modules were packaged. Added the missing product inheritance to
  `device/motorola/sm6150-common/common.mk`; this is the TRY25 candidate.
- Rooted debugging was enabled temporarily with user approval, then `adb unroot`
  returned adbd to the normal shell domain. The user should disable the Rooted
  debugging toggle after diagnostics.
