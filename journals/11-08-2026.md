- Audited the complete project history, the QTI AIDL boot-control source used by
  Recovery and Android, the current Soong graph and variables, and the exact
  TRY32 output retained on the host. No device partition write, reboot, slot
  switch, or update was issued.
- The source path actually compiled is
  `hardware/qcom-caf/bootctrl/1.1/libboot_control_qti/libboot_control_qti.cpp`.
  `out/soong/build.lineage_odessa.incremental.ninja` contains it for both QTI
  AIDL services and does not use the legacy top-level implementation for those
  services. `soong.lineage_odessa.variables` sets
  `XBL_SLOT_BY_GPT_ATTRIBUTES=true` and `USE_BSG_FRAMEWORK=false`.
- Current bootctrl `9c255f8b` implements the TRY14 hardware-proven state exactly:
  target/inactive `boot` = `0x3f`/`0x3a`; target/inactive non-boot partitions,
  including XBL, = `0x04`/`0x00`; and the UFS boot-LUN write is disabled. The
  TRY32 target-files Recovery boot-control binary matches the current output at
  SHA-256 `aa7d0dea54c6f17e6fa583966fd9bf8f809d28d069640da67d9c28661e4d8ee1`.
- Found one definite reproducibility defect: `manifests/odessa.xml` pinned
  `6a856787`, the incomplete implementation that writes every active partition,
  including `boot`, as `0x04`. Updated the pin to the published complete commit
  `9c255f87d5eff9b5b086a65666684733d5b2a225` and documented the hybrid encoding
  in the manifest comment.
- This stale pin does not yet explain the observed TRY26-TRY32 failures. Those
  builds appear to have used the later local source. No immediate post-install
  GPT capture was retained for those reproductions. TRY26 establishes that the
  target reached retry count zero and then booted after `fastboot set_active`
  reset it to seven; it does not establish why the seven attempts failed.
- Earlier evidence warns against treating `fastboot flash partition gpt.bin` as
  proof of GPT repair: after TRY15 that command left every captured GPT region
  byte-for-byte unchanged. A successful boot afterward can instead result from
  MBM resetting/selecting slot state or from another intervening action.
- The current phone is exact TRY32 on slot A and exposes the AIDL
  `android.hardware.boot.IBootControl/default` service. Shell cannot call
  `bootctl` or read the root-owned boot-service binary under the present SELinux
  and Magisk authorization state, so the runtime binary hash and GPT could not
  be collected from Android. No security policy was weakened for inspection.
- Do not set the target successful during activation and do not remove fallback.
  That would conceal the failure and risk leaving a nonbooting update selected.
  The next controlled update needs read-only GPT captures at three checkpoints:
  before installation, immediately after status 0 while still in Recovery, and
  after the first failed automatic boot before any stock GPT flash or manual
  `set_active`. Retain Recovery's update log and the failed boot's boot reason at
  the same checkpoint.

## Controlled TRY32 reproduction and root cause

- Exact TRY32 sideloaded from Recovery A to B and completed status 0.
  `FilesystemVerifierAction` and `PostinstallRunnerAction` both returned
  `kSuccess`; update_engine logged `Update successfully applied`. The immediate
  post-install GPT had valid primary/backup CRCs on every captured LUN and the
  intended active-B encoding: `boot_b=0x3f`, every other B partition `0x04`,
  `boot_a=0x3a`, and every other A partition `0x00`. Type GUIDs swapped between
  the ordinary A/B pairs; unique GUIDs and partition layouts did not change.
- The automatic boot exposed Motorola Android USB but never ADB, consumed every
  B retry, marked only `boot_b=0x80`, and fell back to fully booted TRY32 A.
  MBM restored every other GPT byte to the pre-install state. This proves there
  was no partition-table corruption or split boot chain.
- Read-only hashes after fallback prove installed `boot_b`, `dtbo_b`,
  `recovery_b`, and the 8 KiB `vbmeta_b` are byte-identical to exact TRY32
  target-files. Update_engine had already hash-verified the dynamic partitions.
  Image corruption is eliminated.
- With explicit user authorization, `fastboot set_active b` reset B's retry and
  unbootable state. `running-boot-lun` remained 2. Installed exact Recovery B
  booted. Comparing MBM's selected-B GPT against bootctrl's post-install GPT
  found active B and every GUID identical; the sole semantic difference was the
  inactive known-good A state. Bootctrl cleared it to non-boot `0x00` and
  `boot_a=0x3a`; MBM retained successful A as non-boot `0x40` and
  `boot_a=0x72`.
- Android B then booted immediately from MBM's state. USB exposed Android after
  about 21 seconds and ADB remained available; exact TRY32 reached boot complete
  on B. Android's normal `markBootSuccessful` changed B non-boot `0x04→0x44`
  and `boot_b 0x3f→0x77`, with no other GPT change.
- At this checkpoint we inferred that MBM required the inactive known-good slot
  to retain its successful fallback encoding while trying the new slot. TRY33
  later disproved that as the sole boot-failure cause: `set_active` also changed
  the boot LUN used on the next boot. Preserving fallback remains the safe MBM-
  matching behavior, but it was not the missing activation operation by itself.
- Updated both bootctrl implementation copies. Under the Odessa gate, an
  inactive non-boot partition now retains only its prior successful bit; an
  inactive successful boot partition becomes `0x72`, while an unsuccessful one
  remains `0x3a`. Target activation still overwrites boot with `0x3f`, non-boot
  with `0x04`, clears stale unbootable state, swaps type GUIDs, and leaves the
  boot LUN untouched. The candidate passes `git diff --check` and is unbuilt.
- Enhanced host-only `tools/decode-gpt.py` to report type- and unique-GUID
  changes in addition to layouts and A/B attributes. Python compilation and all
  existing capture comparisons pass.

## TRY33 hardware result and final boot-LUN isolation

- RAM-booted exact TRY33 Recovery on source B; incremental `1786474177`, battery
  100%, and Recovery boot-service SHA-256 `ad7cf2cc...c4510` matched the verified
  artifact. Exact TRY33 installed B-to-A with status 0. Immediate post-install
  GPT CRCs all passed and source behavior was exact: target A `0x04` with
  `boot_a=0x3f`; inactive successful B `0x40` with `boot_b=0x72`; ordinary type
  GUIDs swapped; unique GUIDs and layouts did not change.
- Automatic target A still failed all retries and fell back to boot-complete
  TRY32 B. The post-fallback GPT cleanly restored B and marked only
  `boot_a=0x80`. No new target-kernel `SYSTEM_LAST_KMSG` was retained, so the
  attempt did not yield a kernel crash path. This hardware-disproves the earlier
  conclusion that clearing successful fallback was the sole refusal cause.
- Before the next approved manual selection, bootloader reported
  `running-boot-lun: 3`. `fastboot set_active a` then selected A. Installed exact
  TRY33 Recovery A booted, and its GPT capture was byte-for-byte identical to the
  failed immediate post-OTA GPT. Installed TRY33 Android A subsequently reached
  boot complete. A read-only bootloader query afterward reported
  `current-slot: a`, `running-boot-lun: 2`.
- This is decisive: with GPT bytes held constant, boot LUN 3 fails target A and
  boot LUN 2 boots it. Odessa requires the GPT-selected XBL chain and UFS
  `bBootLunEn` to move together. The old degraded one-slot state occurred when
  upstream moved only the boot LUN and skipped XBL GPT attributes; later code
  fixed the GPT half by disabling the LUN half, creating the current symmetric
  failure. Neither operation is optional.
- Final local candidate removes the `XBL_SLOT_BY_GPT_ATTRIBUTES` early return
  from `gpt_utils_set_xbl_boot_partition()` and removes that now-unused define
  from `libgptutils.qti`. The flag continues to make every XBL-chain partition
  follow GPT attributes in bootctrl. The successful-fallback encoding from
  TRY33 remains. `USE_BSG_FRAMEWORK=false` keeps the 4.14-supported `/dev/sg*`
  UFS query path. Corrected stale comments in bootctrl, common configuration,
  and the manifest. Build and hardware validation are pending; do not call
  TRY33 fixed.
