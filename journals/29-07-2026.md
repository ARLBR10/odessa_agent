## Motorola A/B attribute encoding fix

- A controlled before/after capture of the next successful sideload disproved
  partition-table corruption and the earlier split-XBL regression. All primary
  and backup GPT CRCs remained valid, all A/B partitions switched together, and
  the UFS boot LUN remained pinned to 2. The failing bootctrl encoded slot B as
  Qualcomm `0x3f` active and slot A as `0x40` inactive/successful.
- Recovery B, DTBO B, vbmeta B, the safe A/B firmware pairs, and the OTA payload
  were all hash-verified. Recovery B's kernel, ramdisk, DTB, and recovery-DTBO
  were byte-identical to the working slot-A image. A temporary `fastboot boot`
  of that image also failed while the Qualcomm attributes selected B, exhausting
  B's retries without degrading the bootloader's two-slot partition view.
- Motorola MBM's measured working `fastboot set_active` operation uses exactly
  `0x04` for every active partition and `0x00` for every inactive partition.
  Updated both copies of bootctrl's `UPDATE_SLOT` macro so only devices setting
  `XBL_SLOT_BY_GPT_ATTRIBUTES` use that exact encoding; upstream Qualcomm
  behavior remains unchanged for other devices.
- The user built and flashed the candidate Recovery. The running AIDL service
  matched the host SHA-256
  `3fce8792d7d58dc6bf31b33ada922b4cb0867aa8a2f68ca862fe5771cab56522`;
  both recovery partitions matched the new image, and the kernel remained
  `4.14.357-openela-perf+` from `70aea3b5f901`.
- A second sideload completed with status 0. Direct before/after measurement
  showed every slot-A partition become exactly `0x00` and every slot-B partition
  become exactly `0x04`, including `xbl`, `xbl_config`, `multiimgoem`, and
  `multiimgqti`; primary and backup copies agreed. `adb reboot recovery` then
  booted Lineage Recovery successfully from slot B, hardware-verifying the fix.
- Raw GPT captures and the recovery log were kept only under `/tmp/opencode`, per
  user instruction; none were saved in the workspace. The two bootctrl source
  files were committed and pushed as `6a85678788e1`; the temporary non-BPF
  Odessa property correction was pushed as `6518db3a8131`. The manifest now pins
  both immutable revisions.
